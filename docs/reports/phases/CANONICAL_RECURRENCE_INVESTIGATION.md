Status: investigation in progress; no firmware remediation approved or deployed.

Production requirement confirmed by the user: HOME WI-FI is primary for both ESP32 STA and the registered Owner Android browser. Access and Management must use the unchanged canonical origin without switching networks. Protected AP is secondary recovery only; its availability cannot substitute for home-LAN acceptance.

## Lifecycle source findings

Boot starts the protected configured AP, wildcard UDP53 DNS, canonical mDNS and HTTP, then starts saved STA in AP+STA mode. The main loop updates NetworkManager, CanonicalOrigin, LINE, captive DNS and HTTP. Canonical label is derived from the unchanged full 48-bit hardware identifier. Access and Management use the canonical origin and request a five-minute fallback lease.

The installed Arduino SDK reports ESP-IDF 4.4.7. Version-matched upstream `components/mdns/mdns.c` registers Wi-Fi/IP handlers, enables interfaces already carrying addresses at initialization, enables/probes AP on AP_START, disables AP on AP_STOP, disables STA on disconnect, and enables/restarts its PCB on STA_GOT_IP. Therefore AP-first initialization and ordinary GOT_IP-driven reconnect/address changes are supported by the library. This source behavior does not prove every event was processed in the live incident.

Source: https://raw.githubusercontent.com/espressif/esp-idf/v4.4.7/components/mdns/mdns.c

`c229d41` retained the responder across changes, disabled modem sleep and updated TXT to trigger announcements. `979fc74` removed that TXT mutation, retaining IDF event responsibility. No runtime evidence yet proves the removal caused the recurrence; restarting the responder or restoring allocation-producing TXT mutation is not justified yet.

The protected fallback was introduced in `2b4fcf2`, before `c229d41`. `870ec7f` removed the complete TFT Wi-Fi QR presentation/touch path, while preserving internal AP activation and `buildFallbackWifiQr`. Thus fallback existence and user ability to join it are separate requirements. A home-Wi-Fi client does not use the AP DNS merely because the AP is enabled. No current PC protected-AP profile exists, so AP association and canonical-origin acceptance are not yet tested.

Source initializes the existing HTTP server for port 80; actual reachability requires live probes. Numeric-IP HTTP and explicit Host headers cannot establish successful canonical name resolution. Authentication and authorization layers have not been changed.

## Current LAN wire evidence

The corrected `evidence/canonical_recurrence/lan-before.json` uses the full `.local` FQDN. All three rounds recorded numeric `/health` HTTP 200, direct unicast mDNS A responses from the board naming the exact canonical host and STA address, and board UDP53 wildcard responses pointing to the AP address. The PC resolver and actual canonical `/health` failed in all three rounds. Neither multicast QU nor joined-socket QM returned a response. Router DNS `192.168.1.1` returned RCODE 3 (NXDOMAIN) in all three rounds.

This proves the board responder still knows the canonical name and HTTP is reachable by unicast in these samples. It localizes the observed PC failure to name resolution/discovery, but does not distinguish multicast loss at the board, wireless network or PC receive path. It does not establish which resolver the Owner Android used. Board UDP53 returning the AP address via STA is not a valid LAN remedy.

The first exploratory probe queried a bare label and was rejected during Astra review; its output was replaced by the corrected FQDN run. Only the corrected JSON is evidence. Current Owner phone network is not yet confirmed. Zero AP clients in serial samples is not proof of its earlier connection path.

## Home-LAN discrimination follow-up

The PC remains on 5 GHz channel 48, IPv4 192.168.1.145/24, gateway 192.168.1.1, Windows Public network profile. PktMon is present, but `pktmon status` is denied in the current non-administrator process. Npcap/tshark and ADB were not available. The unauthenticated router root answered HTTP 200 but did not identify a model.

An enabled UDP inbound Python rule covers the installed Python 3.12 executable on Public networks; the earlier Python 3.14 probe executable has no corresponding explicit application rule. Testing the same unchanged mDNS matrix with both interpreters produced identical results: ephemeral-source direct unicast QU/QM returned the exact canonical A address in 4/4 samples per interpreter. Every multicast-destination case and every source-port-5353 case returned no matching response (0/12 per interpreter), despite successful bind/group join and multicast TTL 255. Evidence: `mdns-matrix-python314.json`, `mdns-matrix-python312.json`.

Therefore the application-rule difference alone does not explain these samples. Multiple applications share port 5353, and socket-level absence still cannot distinguish Windows receive handling from Wi-Fi/router forwarding or board multicast behavior. No firmware, firewall, router or stored Wi-Fi configuration was changed. The next discriminator is a bounded NIC capture of the exact mDNS probes, preserving packet direction and canonical answer metadata only. OS elevation is required for that capture; it has not yet run.
